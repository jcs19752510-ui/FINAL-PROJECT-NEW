## 0. 이 문서의 성격 (먼저 읽을 것)

이 기획서는 원 기획팀의 "웹 AI 모의면접 프로젝트 계획서.pdf"(이하 원 계획서)를 그대로 승계한 것이 아니다. `docs/harness/decisions.md`(DEC-001~007)에서 이미 확정된 제약(로컬서버 단일 인스턴스, 유료 API 전면 불가→오픈소스 대체, Oracle→PostgreSQL, 동시접속 500명→50명, Tier=High, MCP 미연동) 위에, 01단계 트렌드 분석에서 확인된 시사점(특히 규제 리스크·AI 세이프티·응답지연 재검증 필요성)을 반영해 **오픈소스 전용·로컬서버·50명 동시접속·Speed Track L1(최고속, 기본값이며 v3의 L3 예외는 §6.4 참고) 제약 안에서 실행 가능한 MVP로 범위를 재산정**한 결과물이다. 원 계획서의 REQ-F-001~007, REQ-N-001~004는 "그대로 구현할 목표"가 아니라 "기능 요구사항의 근거 자료"로만 활용했다(오케스트레이터 지시사항).

**추가 조사 수행**: 01단계에서 "로컬서버 하드웨어 스펙 미확인(Critical)"으로 남겨진 공백을 메우기 위해, 본 단계에서 현재 작업 환경의 실제 하드웨어를 직접 조회했다(`nvidia-smi`, PowerShell `Get-CimInstance`). 결과: **CPU Intel Core i5-1135G7(4코어/8스레드), RAM 32GB, GPU NVIDIA GeForce GTX 1650 Ti(VRAM 4GB)**. 이는 노트북급 사양이며, 대형 GPU(RTX 4070/4090급)를 전제로 한 01단계의 벤치마크 수치와는 거리가 멀다. **단, 이 머신이 실제 운영될 "로컬서버"와 동일한지는 확인되지 않았다** — 이 조사로 완전히 결론이 난 것이 아니라, "확인 가능한 유일한 실측 데이터"를 최소 성능 기준선(baseline) 가정으로 채택한 것이며, 이는 8번 가정 섹션(A1)과 `decisions.md`(DEC-009, 에이전트 자체판단)에 명시했다. 실제 운영 서버 사양이 확인되면 3단계(설계)에서 즉시 재검증해야 한다.

**v3 계획 변경 요약 (규칙 F, DEC-029~032)**: unit-7 진행 중 코드 실측으로, 어느 작업 단위에도 배정되지 않은 갭 3건(내 면접 목록 API·지원자 홈 / 면접장 화면의 컴포넌트 미배선 / 자동 파기 배치 미구현)과 검증 수단 갭 1건(테스트 코드 저장소 미보존)이 발견되어 작업 단위를 **18개(unit-1~18) → 22개(unit-1~22)**로 늘렸다(신규 unit-19~22, §9). 업무 단위(Feature)는 **A~H 8개 → A~I 9개**(신규 Feature I "면접장 통합 UI"; unit-22는 feature가 아닌 공통 인프라라 Feature 수에 포함하지 않음)다. **신규 REQ-ID는 만들지 않고 기존 REQ에 매핑**했으며(REQ-002, 008, 015, 017, 030, 033), 03·04 설계 근거는 이미 존재해 설계 변경은 없다(앵커 실존 확인 결과는 §10 v3 행). 위 첫 문단의 "DEC-001~007"과 "Speed Track L1"은 v1/v2 작성 시점 기준 서술이며, v3에서 DEC-029~032가 추가되었다.

## 1. 서비스/기능 개요 및 목적

**서비스명(가칭)**: 웹 기반 AI 모의면접 플랫폼

**목적**: 구직자(지원자)가 시간·장소 제약 없이 AI 면접관과 실전형 모의면접을 연습하고, LLM 기반 적응형 꼬리질문·STAR 구조 피드백 리포트·루브릭 기반 채용 적합도 점수를 받을 수 있게 한다. 채용 담당자는 지원자 리포트를 열람하고 최소한의 질문지/루브릭 커스터마이징을 할 수 있다.

**1단계 시사점과의 연결**:
- 01단계 §2.1~2.2: "AI 대 AI"(지원자는 AI로 자소서를 쓰고 기업은 AI로 평가하는) 채용 구도 확산, 지원자의 "AI 면접 학습 니즈" 증가라는 사회적 동향이 본 서비스의 존재 이유를 뒷받침한다.
- 01단계 §3: 코드잇 '어센트' 등 지원자용 AI 모의면접 서비스가 이미 시장에 출시되어 있으나, 마이다스인·제네시스랩처럼 "채용담당자 실사용 + 지원자 연습"을 한 플랫폼에서 결합한 사례가 참고 모델이 된다 — 본 서비스는 이 하이브리드 포지션을 지향하되, 4번 섹션(범위)에서 지원자 경험을 우선한다.

원 계획서 REQ-F-001~007, REQ-N-003·004를 전수 검토한 결과, **전부를 그대로 In-Scope로 넣을 수 없다** — 근거: (1) 실측 GPU가 4GB VRAM급으로 실시간 영상 분석·대형 LLM 동시 서빙에 부적합, (2) 얼굴/음성 기반 감정 분석은 EU AI Act가 "고위험/금지 관행"으로 논의 중인 영역이자 국내 개인정보보호법상 생체정보 소지 리스크가 있음(01단계 §5.1, §5.3), (3) Speed Track L1(최고속, `decisions.md` DEC-003)은 무거운 실시간 멀티모달 파이프라인과 궁합이 나쁨, (4) 임의 코드 실행 샌드박스는 원 계획서에 없던 신규 보안 위험을 만듦. 따라서 아래와 같이 우선순위를 매겨 분리한다.

## 5. 성공 지표 (KPI)

> **원 계획서의 "End-to-End Latency 800ms~1.5s"는 유료 스트리밍 API(Deepgram, ElevenLabs) 전제로 설정된 수치이며, 오픈소스/로컬 스택+턴제 응답 방식으로 전환한 이 MVP에는 그대로 적용할 수 없다(01단계 §2.3, §8 시사점 3번).** 아래는 실측 하드웨어(§0)를 기준으로 재정의한 잠정 목표이며, **정확한 수치는 3단계에서 실제 프로토타입 벤치마크로 검증·확정한다**(가정 A2). 벤치마크 결과가 아래 목표와 크게 다르면 변경 이력에 기록하고 필요 시 규칙 F에 따라 재조정한다.

## 6. 제약 조건

### 6.1 기술 제약(하드웨어 실측 반영)
- **실측 baseline**: Intel i5-1135G7(4코어/8스레드), RAM 32GB, GPU GTX 1650 Ti(VRAM 4GB). 7B급 LLM FP16 서빙(약 16GB 필요, 01단계 §2.3)은 이 사양으로 불가능 — **4bit/8bit 양자화된 소형 모델(3B~7B급, 예: llama.cpp/Ollama 기반 GGUF)**을 전제로 설계해야 한다(3단계 몫, 방향성만 제시). *3단계 벤치마크 출발점 예시(확정 아님, 최종 선정은 3단계 실측에 따름)*: 한국어 지원이 알려진 경량 오픈소스 계열(예: Llama 3.1 8B급, Qwen2.5 7B급의 4bit GGUF 양자화판) 등을 우선 후보로 참고할 수 있다.
- STT는 Whisper large급이 아닌 **base/small급 경량 모델**, TTS는 GPU 의존이 낮은 **CPU 구동 가능 모델(예: Piper, MIT 라이선스)**을 우선 검토 대상으로 제시한다. 원안이 언급한 XTTS-v2는 **Coqui Public Model License(CPML)로 비상업 라이선스**이므로(01단계 §2.3), 상업적 서비스 가능성이 있다면 회피하고 Piper 또는 Fish Speech(Apache 2.0) 등을 우선 검토할 것을 권고한다(최종 선정은 3단계).
- DB는 PostgreSQL(DEC-004), 벡터 검색은 pgvector 또는 Chroma(DEC-005) — Pinecone/Oracle 대체 확정.

### 6.2 예산/일정 제약
- 유료 API·클라우드 비용 전면 불가(DEC-005), 로컬서버 단일 인스턴스(DEC-007).
- Speed Track 기본값 L1(최고속, DEC-003) — 06 단위테스트는 경량, 07 통합테스트는 "L1 부채"로 등록되어 08 착수 전 정산 필요. **단 unit-8/10/11 및 unit-19~22는 L3 예외(DEC-031, §6.4)**.
- 원 계획서의 "7주" WBS는 클라우드/유료API/500명 전제의 참고 수치일 뿐이며, 본 프로젝트의 확정 캘린더 일정이 아니다(가정 A8) — 별도 마감일이 필요하면 규칙 A에 따라 언제든 질문 가능.

### 6.3 기존 시스템과의 호환성
- 프로젝트는 그린필드(신규)다. `git log` 확인 결과 기존 커밋은 하네스 자체 세팅(5c5eb66, 63641ee, 2d65ede)뿐이며 기존 소스 코드/도메인 스키마가 존재하지 않는다. 따라서 "기존 시스템과의 호환성" 제약은 해당 없음 — 대신 이 문서 자체가 이후 3~13단계의 기준선이 된다.

### 6.4 Tier/속도 트랙
- Tier=High(DEC-002) — 규칙 B(최소 2회 검증), 9단계 보안검증 등 모든 완화 조항 미적용. (v3에서도 불변)
- 각 업무단위는 기본 L1로 착수(DEC-003), 사용자가 특정 유닛(예: 인증/결제성 로직)에 다른 트랙을 지정하면 예외 적용.
- **L3 예외(DEC-031, v3)**: unit-8/10/11 및 신규 unit-19/20/21/22는 전부 **L3(일반)** — 06·07 정식(10섹션 전체), 규칙 B 원문, 부채 없음. DEC-003(기본 L1)의 예외이며, 이미 L1로 진행된 유닛의 07 미실행 부채를 08 착수 전에 정산해야 하는 의무는 그대로 유지된다. 한 feature 안에 L1 유닛과 L3 유닛이 섞인 경우(예: Feature B·C·G) 07은 그 feature의 전 유닛을 정식으로 커버해 L1 부채를 함께 정산한다(ORCHESTRATOR.md 1장 "되돌릴 수 없는 안전장치" 1번). unit-22는 feature가 아닌 공통 인프라이므로 07 대상이 아니며 06까지만 수행한다(DEC-030).
