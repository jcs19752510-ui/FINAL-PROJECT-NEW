# unit-26 구현 노트 — 원안 LangChain 오케스트레이션 검증

- 작성 에이전트: 본 세션(05+06 역할 겸임), 작성일: 2026-09-22
- 원 계획서 §4.2: "LLM 에이전트 개발: LangChain을 이용한 면접관 페르소나 구현,
  대화 상태 관리(Memory) 로직"

## 1. 스코프 결정 (운영 파이프라인을 왜 안 바꿨는가)

`app/services/llm_engine.py`는 오늘(2026-09-22) 실제 음성 제출 장애가 발생했던
`interviews.py`와 같은 백엔드 모듈군이며, 그 자체로도 unit-7에서 11건의 실측
결함(질문형 검증 실패, 워커 크래시 시 job 유실, llama-server 이중바인드 등)을
거쳐 안정화됐다. "LangChain으로 전환"이 원안 스펙과 "일치"하려면 이 파일 자체를
LangChain으로 바꿔야 하지만, 다음 이유로 **운영 파이프라인은 건드리지 않고
별도의 검증 모듈로 실제 동작을 증명하는 방식**을 택했다:

1. 프레임워크 전환은 기능 추가가 아니라 순수 리팩터링이라 실익이 낮음(③ 매트릭스
   근거란 기존 판단과 동일).
2. 이미 안정화된 GPU/CPU 폴백, 이중바인드 방지, 구조화출력 재시도 로직
   (`_ensure_server_running`, DEF-009 등)을 다시 구현하면 같은 결함을 재도입할
   위험이 있음 — 대신 그 함수를 **그대로 재사용**했다.
3. 이 환경에 브라우저 테스트 도구가 없어 실제 사용자 트래픽으로 회귀를 검증할
   방법이 없음(unit-24의 STT 스트리밍 보류와 동일한 제약).

## 2. 구현 범위

- `backend/app/services/langchain_orchestrator.py`(신규): `langchain_openai.
  ChatOpenAI`로 기존 llama-server의 OpenAI 호환 엔드포인트를 감싼다.
  `with_structured_output()`(도구 호출 기반, llama-server 지원 여부 미검증)
  대신 `llm_engine.py`가 이미 실측 검증한 "JSON 모드 + 수동 Pydantic 파싱 +
  1회 재시도" 패턴을 그대로 따른다.
- `_ensure_server_running`(llama-server 기동/폴백)을 `llm_engine.py`에서 그대로
  import해 재사용 — 복제하지 않음.
- `backend/requirements.txt`: `langchain-core`, `langchain-openai` 추가, 실제
  설치·동작 확인.

## 3. 실측 검증 결과 (테스트 보고서 요약, 상세는 unit-26-test.md)

- 기존에 이미 가동 중이던 llama-server(포트 8091, 다른 세션/Celery 워커가 띄운
  것)를 그대로 재사용해(이중 기동 없이) 실제 한국어 꼬리질문 생성 성공(1.27초).
- **부수 발견**: 이 테스트로 생성된 텍스트를 UTF-8 파일에 직접 기록해 확인한
  결과 **손상 없는 정상 한국어**였다. 이는 unit-24가 발견한 `content_text` DB
  손상 결함의 원인이 "LLM이 애초에 깨진 텍스트를 생성한다"가 **아니라**, 생성된
  정상 텍스트가 이후 어딘가(Celery/Redis 직렬화, DB 저장 경로 등)에서 손상된다는
  강한 단서다 — 별도 조사(사용자 지시로 6개 항목 이후 진행)에 인수인계.
- 재시도 로직(파싱 실패 1회 재시도 후 에러) 양쪽 분기 모두 통제된 가짜 응답으로
  실제 코드 실행 검증(모킹은 LLM 호출부만, 재시도/파싱/예외 처리 로직 자체는
  실제 실행).

## 4. 범위 밖 (인수인계)

- RAG(질문은행 검색)를 LangChain 리트리버 추상화로 재구현하지 않았다 — 이미
  `rag_engine.py`가 pgvector+MMR로 동작 중이고, 이 유닛의 목적(오케스트레이션
  레이어가 LangChain으로 실제 동작 가능함을 증명)에는 불필요한 추가 범위라
  제외했다. 필요 시 후속 작업으로 가능.
- LangGraph(멀티턴 상태 그래프)는 다루지 않았다 — `llm_engine.py`가 이미
  DB(TRANSCRIPTS 이력 창)로 멀티턴 컨텍스트를 관리하고 있어 동등 기능이 이미
  존재, 이번 유닛은 "LangChain 오케스트레이션 자체가 이 환경에서 동작하는가"
  검증에 집중했다.
- **운영 전환 여부는 사용자 결정 필요** — 이 모듈은 존재하고 검증됐지만
  `worker/tasks.py`가 이를 호출하도록 바꾸지는 않았다.
