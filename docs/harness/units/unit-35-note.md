# unit-35 구현 노트 — 화이트보드 AI 비전 분석 (원안 REQ-021, 부분 구현)

- 작성 에이전트: 본 세션(05 인계 확인 + 06 역할), 작성일: 2026-09-23
- 배경: `backend/app/services/whiteboard_vision.py`(신규 파일)는 직전 세션에서
  이미 작성돼 있었고 파일 docstring에 "2026-09-23 사용자 승인, unit-35"라고
  기록돼 있었으나, 정식 06단계 테스트 결과서·`decisions.md`·`traceability.md`
  반영이 전혀 없는 상태(규칙 G/H 공백)로 세션이 중단됐다. 이번 세션은 이 인계
  상태를 확인하고, 실제 실행 검증과 정식 문서화를 완료하는 역할을 맡는다
  (DEC-050 참고. DEC-037과 동일한 유형의 절차 공백이며, 함께 발견된 unit-23~34의
  동일 공백 12건도 이번 세션에서 DEC-038~049로 소급 정리했다).

## 1. 인계 시점 상태 확인 (이번 세션이 직접 재현·검증한 것)

- `render_strokes_to_png()`: 좌표 스트로크 배열을 실제 PNG로 래스터라이즈하는
  순수 함수(Pillow만 사용, 외부 네트워크/API 의존 없음). 이전 세션이
  `.harness-tmp/whiteboard_render_test.png`를 생성한 흔적은 있었으나(규칙 K에
  따라 이번 세션 시작 시 `.harness-tmp/` 전체를 사용자 승인 하에 정리하며 함께
  삭제됨), 그 결과를 담은 정식 테스트 결과서는 없었다 — **이번 세션이 처음부터
  다시 실행해 재검증**했다(§2 참고).
- `analyze_diagram_with_vision()`: OpenAI GPT-4V(`gpt-4o`) Chat Completions
  호출. API 키가 없어 실제 네트워크 호출은 여전히 불가능 — unit-32 벤더
  어댑터와 동일한 제약. 다만 이번 세션은 `unittest.mock`으로 `urlopen`을
  대체해 **응답 파싱·에러 변환 로직만은 실제로 실행해 검증**했다(unit-32에는
  없었던 추가 검증, §2 TC-008~010).

## 2. 발견·수정한 결함 (이번 세션)

- **DEF-001(Low, Fixed)**: `backend/requirements.txt`에 `Pillow` 선언이
  누락돼 있었다. `backend/.venv`에는 이미 설치돼 있어(12.3.0) 이번 세션에서는
  증상이 드러나지 않았지만, 신선한 환경(`pip install -r requirements.txt`)에서는
  `ImportError`로 즉시 깨졌을 것이다. requirements.txt에 unit-35 전용 주석과
  함께 `Pillow>=11.0,<13.0` 추가로 수정.

## 3. API 미배선 결정 (이번 세션 판단, DEC-050)

`render_strokes_to_png()`는 완전히 검증됐지만, 어떤 API 엔드포인트에도
연결하지 않았다. 이유:
1. 이 기능의 사용자 가치는 "렌더링" 자체가 아니라 "AI가 다이어그램을 보고
   타당성을 평가"하는 것(원안 목표) — 비전 호출 없이 렌더링만 노출하는 반쪽
   엔드포인트는 아무도 요청하지 않은 기능이다.
2. 비전 호출부(`analyze_diagram_with_vision`)는 API 키가 없어 배선해도 항상
   실패한다 — unit-32(벤더 어댑터 3종)가 이미 확립한 선례와 동일한 판단
   기준(코드는 준비하되 실제 자원 확보 전에는 연결하지 않음)을 그대로 따랐다.
3. `backend/app/api/v1/whiteboard.py`의 기존 라우터는 DEC-008 시절 작성된
   docstring에 "이미지 인식/비전 모델 호출 코드는 포함하지 않는다"고 명시돼
   있다 — 이 문서(그 자체가 이제 부분적으로 낡은 설명이 됨)를 갱신하지 않은
   채 그 라우터에 비전 호출을 끼워넣는 것은 그 파일을 소유한 unit-17/20의
   경계를 침범하는 일이라 이번 세션 범위에서 배제했다(신규 엔드포인트를
   추가한다면 unit-14/whiteboard.py 선례처럼 독립 라우터로 분리해야 한다는
   점을 후속 작업 메모로 남긴다).

**결론**: REQ-021은 "부분착수" 상태를 유지한다. API 키 확보 + 실제 배선
결정(엔드포인트 설계, 09단계 감사)이 모두 있어야 "완료"로 승격 가능하다.

## 4. 원 계획서 대비 편차

- 원안은 "다이어그램 인식 → 아키텍처 타당성 평가"라는 완결된 기능을 전제하나,
  이번 유닛은 그 전반부(좌표→이미지)만 실제로 동작한다. 후반부(이미지→평가)는
  키만 있으면 즉시 시도 가능하나 **단 한 번도 실행된 적이 없다.**
- `_CANVAS_SIZE = (1200, 800)`는 04-ux-design 캔버스 좌표계를 가정한 값이며,
  실제 프론트엔드 `WhiteboardCanvas.tsx`의 캔버스 픽셀 크기와 다를 경우
  좌표가 잘리거나 여백이 생길 수 있다 — 이번 세션은 이 가정을 프론트 코드와
  대조 검증하지 않았다(범위 밖, 후속 확인 필요 항목으로 §5에 기록).

## 5. 후속 확인 필요 항목

1. `_CANVAS_SIZE`(1200×800)가 실제 프론트 캔버스 크기와 일치하는지 대조.
2. GPT-4V API 키 확보 시: unit-32 어댑터들과 함께 정식 06단계 실네트워크
   재검증 필요.
3. 실제 배선 여부·엔드포인트 설계는 사용자 확인 후 별도 unit으로 착수
   (예: `POST /interviews/{id}/whiteboard/analyze`, 09단계 이후 권장 — 임의
   코드실행(unit-29)과 달리 RCE 위험은 없으나 vendor 응답을 그대로 사용자에게
   노출하기 전 새니타이즈 필요 여부는 별도 검토).

## 6. 후속 세션 — 로컬 VLM 실연결 (2026-09-23, DEC-061)

사용자가 스펙 비교 문서(`spec-compare.html`)에서 "부분착수" 상태로 남아있던
전환 가능성 매트릭스 항목 중 이 항목을 지정해 재개를 요청했다. 단, GPT-4V(유료)
키를 새로 발급하지 않는다는 기존 방침(2026-09-23 초, "유료 항목은 진행 안 함")은
그대로 유지되므로, §3에서 미배선 이유로 들었던 "비전 호출부가 키 없이 항상
실패한다"는 전제 자체를 다른 경로로 해소했다 — **GPT-4V 대신 로컬 무료 VLM인
SmolVLM-500M-Instruct**를 llama.cpp `llama-server`(llm_engine.py의 Qwen
서브프로세스와 동일 패턴, 포트만 8093으로 분리)로 구동해 실제로 연결했다.

- **신규 함수**: `whiteboard_vision.analyze_diagram_local(png_bytes)`. §3에서
  거론했던 "독립 라우터로 분리" 방향을 그대로 따라 `whiteboard.py`(unit-17/20
  소유 파일)에 새 엔드포인트 `POST /interviews/{id}/whiteboard/analyze`만
  추가하고, 기존 PUT/GET 두 엔드포인트는 건드리지 않았다.
- **실측 품질**: 직전 세션의 `.harness-tmp/test_smolvlm500_probe.py` 프로브
  결과(한 단어/단편 답변)가 이번 실제 연결에서도 그대로 재현됐다 — 박스 2개 +
  화살표 1개로 이루어진 테스트 다이어그램에 "이 이미지의 박스와 라벨을
  설명하라"고 묻자 모델은 `"2"` 한 글자만 반환했다(§ unit-35-test.md TC-011
  로그 참고). **품질 개선 시도는 하지 않고 그대로 연결**하기로 사용자가
  명시적으로 결정했으므로(정확도 조건 없음), 모든 응답에 저신뢰
  disclaimer(`LOW_CONFIDENCE_DISCLAIMER`)를 항상 동봉해 사용자가 결과를
  맹신하지 않도록 하는 것으로 이 결정을 반영했다.
- **지연시간 실측**: 서버 최초 기동 포함 31.0초(모델 로드+헬스체크 대기),
  서버가 이미 떠 있는 상태에서 재호출 시 0.4초. Qwen(8091)과 별도 프로세스라
  두 모델이 동시에 상주해도 포트 충돌은 없다(VRAM/RAM 여유는 실측하지 않음 —
  이 환경은 내장 GPU라 Qwen도 CPU 폴백 상태였을 가능성이 높음, 후속 확인 필요).
- **검증 수준**: 서비스 계층(`render_strokes_to_png`→`analyze_diagram_local`
  직접 호출)은 실제 SmolVLM 서버에 대해 2회 실행(cold/warm)으로 검증했다.
  FastAPI 앱 구성 시 신규 라우트가 정상 등록됨을 `app.routes` 조회로 확인했고,
  프론트엔드(`WhiteboardCanvas.tsx`, `lib/api.ts`)는 `tsc --noEmit` 통과로
  검증했다. **후속(같은 날, 사용자 요청): Docker Desktop을 실제로 기동**하고
  (최초 구동이라 약 4분 소요), 기존 `final-project-db`/`final-project-redis`
  컨테이너 재기동 + uvicorn 실행 + httpx로 회원가입→로그인→면접생성→화이트보드
  저장→`POST .../whiteboard/analyze` 전 구간을 실제 HTTP로 검증 완료(unit-35
  -test.md TC-015, 200 OK, 응답 `{"analysis":"2","disclaimer":"...","model":
  "SmolVLM-500M-Instruct (local)"}`). 테스트로 생성한 계정 2건·면접 2건·
  스냅샷 2건은 검증 직후 삭제(규칙 K). 이로써 §7의 후속 확인 4번 항목은 해소됐다.
- unit-32 계열과 달리 이 항목은 **엔드포인트까지 실제로 배선했다** — 화이트보드
  캔버스 UI(`WhiteboardCanvas.tsx`)에 "AI 분석" 버튼과 disclaimer 표시 영역도
  함께 추가했다(면접장 메인 레이아웃에는 여전히 삽입되지 않은 독립 컴포넌트
  상태, unit-17 원 노트와 동일 제약).
