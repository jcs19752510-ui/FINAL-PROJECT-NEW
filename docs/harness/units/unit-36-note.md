# unit-36 구현 노트 — STT 실시간 스트리밍 미리보기 (미니 세그먼트 방식)

- 작성 에이전트: 본 세션, 작성일: 2026-09-23
- 배경: unit-24(2026-09-22)가 "오늘 실제 장애가 있었던 코드를 브라우저 테스트
  도구 없이 재설계하는 위험"을 이유로 보류했던 항목(DEC-039). 이번 세션은
  브라우저 도구가 있는 상태에서 사용자 승인을 받아 재개했다(DEC-052).

## 1. 설계 결정 — 왜 "청크 재조립"이 아니라 "미니 세그먼트"인가

사용자에게 두 방식을 제시하고 확인받았다(DEC-052):
- **(기각) 청크 스트리밍**: 브라우저 `MediaRecorder`의 `timeslice` 연속 청크는
  첫 조각에만 WebM 헤더가 있어 이후 조각은 단독 디코딩이 불가능하다 — 서버가
  WebM 컨테이너를 실시간 재조립해야 하는 신규 복잡도가 크고, 오늘 실제 장애가
  있었던 코드 근처를 더 깊이 건드리게 된다.
- **(채택) 미니 세그먼트**: `MediaRecorder` 인스턴스를 4초마다 새로 만들어
  매번 완전한 독립 WebM 파일을 얻는다. 이미 검증된 `transcribe_audio()`를
  그대로 재사용할 수 있고, 최종 제출 경로(`_submit_voice_turn`)를 전혀 건드리지
  않는다.

## 2. 구현 범위 — 완전히 분리된 새 경로

**기존 `_submit_voice_turn`(오늘 실제 장애가 있었던 함수)은 단 한 줄도
수정하지 않았다.** 대신:

- `backend/app/api/v1/interviews.py`: `POST /interviews/{id}/turns/preview`
  신규 엔드포인트(`submit_voice_preview`). 소유권 검사(`_get_own_interview`)와
  `live` 상태 검사만 재사용하고, 나머지(동의 검사·레이트리밋·멀티파트 파싱·
  STT 호출)는 최종 제출과 같은 안전 패턴(`run_in_threadpool`로 블로킹 STT를
  위임 — "장애 대응" 주석과 동일 원칙)을 그대로 따르되 독립적으로 재구현했다.
  DB에 아무것도 쓰지 않고, job도 큐에 넣지 않는다.
- `backend/app/schemas/transcript.py`: `VoicePreviewResponse`(신규, `text`
  필드만).
- `backend/app/services/prompt_safety.py`: `check_and_increment_preview_rate_limit()`
  신규 — 정식 턴 레이트리밋(분당 10회, LLM 트리거용)과 별도의 Redis 키
  (`rate_limit:stt_preview:{user_id}`)로 분당 20회 상한. 정식 턴 한도를
  갉아먹지 않는다.
- `frontend/lib/api.ts`: `submitVoicePreview()` 신규 클라이언트 함수.
- `frontend/app/interviews/[id]/page.tsx`: 녹음 중(`recording===true`) 동안
  같은 마이크 스트림 위에서 **두 번째** `MediaRecorder`를 4초마다 재시작하는
  `runPreviewCycle()`/`startPreviewLoop()`/`stopPreviewLoop()` 추가. 기존
  최종 제출용 `mediaRecorderRef`/`startRecording`/`stopRecording`/
  `handleVoiceUpload`는 호출 지점 두 곳(preview 루프 시작/정지 삽입)만 빼고
  손대지 않았다. 인식 중인 텍스트는 새 상태 `livePreviewText`로 채팅 영역에
  "실시간 인식 중" 말풍선으로 표시된다.

## 3. 실측 검증 요약(상세는 unit-36-test.md)

- 격리된 신규 uvicorn(8503)에 실제 Piper로 합성한 한국어 문장을 흘려보내
  `/turns/preview` 호출 → 응답 텍스트가 원문과 정확히 일치(구두점만 추가)
  확인. 기존 `/turns`(최종 제출) 경로는 회귀 없음(동일한 무음 입력에 동일한
  422) 확인.
- 실제 브라우저(Claude_Browser 내장 도구)로 회원가입→로그인→면접 생성까지
  실행해 프런트 변경이 런타임 에러를 내지 않음을 확인. 단, 사전고지 동의
  화면의 스크롤 게이트(이 유닛과 무관한 기존 컴포넌트)를 자동화로 통과하지
  못해 면접장 화면까지는 이번 세션에서 도달하지 못했다 — §5 참고.

## 4. 실사용 전 필요한 조치 (사용자 확인 필요)

**라이브 개발 백엔드(포트 8010, 프런트가 실제로 바라보는 서버)는 이번
세션의 코드 변경을 아직 반영하지 않은 상태다** — `uvicorn --reload` 없이
떠 있어 재시작 전까지 `/turns/preview`가 404를 낸다. 이 세션은 사용자의
라이브 프로세스를 임의로 재시작하지 않았다(규칙 K, 사용자 작업 중인 세션을
함부로 건드리지 않기 위함). **사용자가 원할 때 백엔드를 재시작해야 이
기능이 실제로 동작한다.**

참고로 이번 세션 시작 시 포트 8000에서 응답 없는(hang) 별도 백엔드 프로세스
(PID 25972)를 발견했다 — 프런트가 실제로 쓰는 포트(8010)가 아니라 당장
영향은 없으나, 이전 세션이 정리하지 못한 좀비 프로세스로 보인다(규칙 K-3,
사용자 확인 후 정리 권장).

## 5. 후속 확인 필요 항목

1. **브라우저 수동 확인 필요**: 백엔드 재시작 후, 실제 마이크로 답변을
   녹음하며 "실시간 인식 중" 말풍선에 텍스트가 실제로 누적 표시되는지,
   최종 제출이 여전히 정상 동작하는지 육안 확인 권장(이 세션은 동의 화면
   스크롤 게이트를 통과하지 못해 여기까지 자동화하지 못함).
2. 두 번째 `MediaRecorder`가 같은 스트림에서 동시 동작할 때 브라우저별
   호환성(Safari/Firefox 등)은 확인하지 않음 — Chromium 계열만 전제.
3. 분당 20회 레이트리밋 상한 자체의 실측(실제로 20회를 초과시켜 429가
   뜨는지)은 이번 세션이 5회까지만 확인했다(§6 unit-36-test.md TC-005) —
   상한값 자체는 구현 세부값(비가역성 낮음)이라 실사용 중 너무 타이트하면
   조정 가능.
