- 관련 산출물: `docs/harness/units/unit-15-note.md`(§6 인수조건, §7 재작업 변경이력), 이전 라운드 결과(FAIL, DEF-001) — 본 파일이 그 위에 덮어써 최종본이 됨, `docs/harness/03-system-design.md` §4.2/§6.2, `docs/harness/04-ux-design.md` [C-04]/[C-13]/[C-14], `docs/harness/traceability.md`(REQ-031~034)

## 12. §11 수정의 회귀 — DEF-003 발견·수정·완전 재검증 (2026-09-24, DEC-064 추가분)

### 12.1 경위
§11의 DEF-002 수정을 사용자에게 "완료"로 보고했으나, 사용자가 직접 테스트한 결과 "새 면접 시작" 클릭 후 화면이 **"새 면접 세션을 만드는 중입니다..."에서 무한정 멈춰있다**는 것과 브라우저 콘솔에 hydration 관련 에러 배지("1 Issue")가 뜬다는 것을 스크린샷 2장과 함께 신고했다. 사용자는 "테스트를 제대로 한 게 맞느냐"고 강하게 항의했다 — **정당한 지적이다**: §11의 재검증은 네트워크 로그로 "POST 요청이 1번만 나갔다"만 확인했을 뿐, **그 요청의 응답으로 실제 화면 전환(다음 페이지 진입)까지 이어지는지를 눈으로 확인하지 않았다.** 이번 절은 그 실수를 인정하고, 이번에는 빠짐없이 재검증한 기록이다.

### 12.2 원인 분석 — DEF-002 수정 자체가 만든 새 결함(DEF-003)
`frontend/app/interviews/new/page.tsx`의 §11 수정본은 `useRef` 가드(`startedRef`)를 추가하면서도, 기존 `cancelled` 클린업 로직을 그대로 남겨두었다:
```tsx
if (startedRef.current) return;
startedRef.current = true;
let cancelled = false;
createInterview(token).then((interview) => {
  if (cancelled) return;          // ← 문제 지점
  router.replace(...);
});
return () => { cancelled = true; };
```
React(개발 모드) Strict Mode의 실제 실행 순서는 "1차 마운트(effect 실행) → 1차 클린업 즉시 실행 → 2차 마운트(effect 실행)"이다:
1. **1차 마운트**: `startedRef.current`가 `false`이므로 통과 → `true`로 설정 → **실제 `createInterview()` 호출이 여기서 나간다.**
2. **1차 클린업**: 위 호출의 클로저에 있는 `cancelled`를 `true`로 세팅한다.
3. **2차 마운트**: `startedRef.current`가 이미 `true`이므로 `return`— 이 마운트는 아무 요청도 보내지 않는다.
4. 잠시 후 1차 마운트에서 보낸 요청이 서버 응답을 받는다 — 세션은 **정상적으로 생성됐다**(서버 로그·DB 모두 정상, §12.3에서 재확인). 그러나 `.then` 핸들러가 `cancelled`를 검사하는데, 이 `cancelled`는 **2단계에서 이미 `true`로 세팅되어 있다** — 그래서 `router.replace(...)`가 영원히 호출되지 않고, 화면은 로딩 문구에서 멈춘 채로 남는다.

즉 "실제 호출은 1회로 줄이는 데는 성공"했지만, "그 유일한 호출의 성공 결과를 화면에 반영하는 경로를 스스로 차단"해버린 것이다. 서버 쪽에서는 아무 문제가 없었기 때문에(세션 생성 자체는 200/201로 항상 성공), 네트워크 요청 횟수만 세는 검증으로는 이 결함이 드러나지 않았다 — 반드시 "그 다음 화면까지 실제로 넘어가는가"를 봐야 발견되는 종류의 결함이었다.

(참고: 사용자 스크린샷의 "1 Issue"/hydration 경고는 `user-select:"auto"` 스타일이 `<html>`/`<body>`에 주입된 것이 원인으로, Next.js 자신도 "브라우저 확장 프로그램이 React 로드 전에 HTML을 건드렸을 때 발생할 수 있다"고 명시하는 패턴과 정확히 일치한다 — 텍스트 선택 허용류 확장 프로그램이 흔히 하는 동작이다. 이 경고 자체는 "패치되지 않고 넘어간다"는 안내대로 기능을 막지 않으며, 화면이 멈춘 진짜 원인은 위 DEF-003이었다. 클린 브라우저 탭(확장 프로그램 없음)으로 재현했을 때도 화면 멈춤은 동일하게 발생했고 hydration 경고는 없었다는 점이 이를 뒷받침한다 — 즉 두 현상은 원인이 다른 별개 이슈였다.)

### 12.3 수정
`cancelled` 클린업을 완전히 제거했다 — `startedRef`가 이미 "실제 호출은 프로세스당 1회"를 보장하므로, 그 유일한 호출의 결과를 그냥 그대로 사용하면 된다(더 이상 "먼저 실행된, 이제는 무효한 호출"이라는 개념 자체가 존재하지 않음). 상세 diff는 파일 상단 주석(2026-09-24 갱신)에 그대로 남겨 이력을 보존했다.
