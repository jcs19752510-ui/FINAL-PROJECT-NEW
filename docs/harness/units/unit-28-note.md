# unit-28 구현 노트 — WebRTC 시그널링 서버 (원안 §2.2, 부분 구현)

- 작성 에이전트: 본 세션(05+06 역할 겸임), 작성일: 2026-09-22
- 원 계획서 §4.1: "Signaling Server: FastAPI(WebSockets), WebRTC 연결 수립(SDP/
  ICE 교환)" / §2.2: "브라우저 간 직접 연결(P2P) 방식보다는 SFU 또는 서버 사이드
  프로세싱 구조를 채택"

## 1. 정직한 스코프 선언 (매우 중요)

이 유닛은 **원안의 WebRTC 요구사항 전체를 구현하지 않는다.** 원안은 시그널링
서버 + 미디어 서버(aiortc/GStreamer, 오디오/비디오 스트림을 실제로 수신·분기)
두 계층을 모두 요구하지만, 이번에 실제로 구현·검증한 것은 **시그널링 서버
(SDP/ICE 중계)뿐**이다. 이유:

1. 미디어 서버(실제 RTP 스트림 디코딩/분기)는 그 자체로 별도의 대규모
   작업이며(③ 매트릭스가 이미 "대"로 분류), 이번 세션에서 "정직하게" 끝낼 수
   있는 범위가 아니다.
2. 이 환경에 브라우저 자동화 도구가 없어 실제 카메라/마이크로 WebRTC 연결을
   맺는 것 자체를 검증할 방법이 없다 — 시그널링(순수 WebSocket 메시지 중계)은
   Python `websockets` 클라이언트 2개로 실측 검증 가능했지만, 실제 미디어
   협상(ICE connectivity check, DTLS handshake, RTP)은 검증 불가능한 채로
   "구현했다"고 주장하는 것은 이 세션 전체가 유지해온 "실제로 실행해서 검증한
   것만 완료로 표시" 원칙에 위배된다.
3. "가짜로 완성된 척"하는 대신, **진짜로 동작하고 검증된 한 조각**(시그널링
   릴레이)을 내놓는 것이 이 프로젝트의 전반적 원칙("가짜 데이터 금지",
   `app/api/v1/ops.py`의 정직한 0 표시 등)과 일관된다.

## 2. 구현 범위

- `backend/app/api/v1/webrtc_signaling.py`(신규): `/ws/interviews/{id}/signaling`
  WebSocket 경로. interview_id당 최대 2피어를 묶어(`SignalingRoomManager`),
  한쪽이 보낸 `offer`/`answer`/`ice-candidate`/`bye` 메시지를 다른 쪽에게 그대로
  중계한다(불투명 릴레이 — SDP 내용을 서버가 해석하지 않음, 일반적인 시그널링
  서버 설계).
- 기존 `app/api/v1/ws.py`(turn_result 등 push 전용 채널)는 **전혀 수정하지
  않았다** — 완전히 별도 경로로 분리해 그 채널에 의존하는 기존 유닛들에 영향 0.
- 인증은 `ws.py`의 `_authenticate()`를 그대로 재사용(복제하지 않음) — 오늘
  실측된 "동기 DB 호출을 threadpool 없이 async 핸들러에서 직접 호출하면
  이벤트 루프가 멈춰 백엔드 전체가 응답불능이 된다"는 장애 패턴(ws.py 자체
  주석에 이미 기록됨)을 재현하지 않기 위해 이미 그 교훈이 반영된 함수를 그대로
  가져다 썼다.

## 3. 실측 검증 (테스트 보고서 요약, 상세는 unit-28-test.md)

Python `websockets` 클라이언트 2개로 실제 서버에 연결해: offer/answer/ice-
candidate 양방향 중계, 발신자에게 자기 메시지가 에코되지 않음, 화이트리스트
밖 메시지 타입 차단, 3번째 피어 연결 거부(방 가득 참), 잘못된 토큰 거부, 기존
turn_result 채널 회귀 없음까지 — 7개 항목 전부 실제 WebSocket 연결로 확인했다.

## 4. 범위 밖 — 실제 완료까지 남은 것 (인수인계)

- **미디어 서버**: aiortc(또는 GStreamer) 기반으로 실제 오디오/비디오 RTP
  스트림을 수신·디코딩하는 별도 프로세스/모듈. 이게 있어야 비로소 "면접관이
  영상을 본다"는 원안의 실제 목적이 달성된다. 이번 유닛은 그 전 단계
  (연결 수립 메커니즘)만 만들었다.
- **프론트엔드**: `frontend/`에는 이 시그널링 엔드포인트를 호출하는 코드가
  전혀 없다(RTCPeerConnection 생성, getUserMedia로 얻은 스트림 연결, offer/
  answer 생성 등 브라우저 측 WebRTC API 사용 코드 전무) — 이번 유닛은 백엔드
  릴레이만 다뤘다.
- **STUN/TURN 서버**: 원안 §6.2.1의 API 예시가 `stun:stun.l.google.com`,
  `turn:turn.mockinterview.com`을 언급했다 — 실제 NAT 통과를 위해 필요하지만
  이번 유닛에서 구성하지 않았다.
- DeepFace 등 감정분석(③ 매트릭스 별도 항목)은 이 미디어 서버가 먼저 있어야
  가능한 후속 작업 — 여전히 미착수.

**결론**: ③ 매트릭스의 "WebRTC 영상 스트리밍 + 미디어서버" 항목은 이 유닛으로
"완료"가 아니라 **"부분 착수"**로 표시해야 정직하다 — 아티팩트 갱신 시 그렇게
반영한다.
