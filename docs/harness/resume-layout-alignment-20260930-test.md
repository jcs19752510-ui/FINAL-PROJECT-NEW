- **작업 일시**: 2026-09-30 (KST)
- **신고자**: 사용자(정찬성), 실제 크롬/엣지 등 별도 브라우저로 `localhost:3002/resume` 접속 후 스크린샷 첨부
- **신고 내용(원문)**: "화면글자들이 정렬이 잘 안되어 있어요. 검토후 조치해 주세요."
- **첨부 스크린샷 특징**: 이력서 제출 카드가 화면 왼쪽에는 큰 여백을 두고 오른쪽으로 치우쳐 보임(카드 자체 내부 요소 정렬이 아니라, 카드 전체 위치가 중앙이 아닌 것처럼 보이는 형태)

## 1. 조사 방법 — 추측하지 않고 실측

코드를 눈으로 읽고 "아마 이게 문제겠지"로 단정하지 않고, 실제 페이지를 로그인 상태로 띄운 뒤
`getBoundingClientRect()` / `getComputedStyle()`로 실제 렌더링 수치를 직접 측정했다(2번 일
시키지 않도록 육안 판단 대신 숫자로 확정하는 것이 목표).

### 1-1. 컨테이너 중앙정렬 계산 검증

| 뷰포트 폭 | 카드 실제 x좌표 | 카드 너비 | 기대 x좌표 `(폭-카드너비)/2` | 오차 |
|---|---|---|---|---|
| 800px | 152.5px | 480px | 160px | -7.5px (세로 스크롤바 폭만큼, 정상 범위) |
| 1280px | 400px | 480px | 400px | **0px** |
| 1920px | 720px | 480px | 720px | **0px** |

`frontend-apply/app/globals.css`의 `.auth-page { display:flex; align-items:center;
justify-content:center; }` 규칙이 실제로 정확히 동작하고 있음을 확인했다. 테스트한 모든
뷰포트 폭에서 카드는 수학적으로 정확히 가운데였다 — "오른쪽으로 크게 쏠림" 현상은
**이 세션의 Claude 브라우저 프리뷰 창(Browser pane)에서는 재현되지 않았다.**

### 1-2. 가로 스크롤/오버플로 여부

```
docScrollWidth === docClientWidth (785 === 785) → 가로 스크롤 없음
hasHorizontalScrollbar: false
```

페이지 내부에 뷰포트보다 넓은 요소가 숨어있어 정렬 기준점이 틀어지는 경우도 아니었다.

### 1-3. 스크린샷 출처 확인 (사용자 답변)

이 세션과 공유되는 Browser pane에서 찍은 것인지, 별도의 실제 브라우저(크롬/엣지 등)로 직접
접속해 찍은 것인지 사용자에게 직접 확인했다 — **"실제 크롬/엣지 등 다른 브라우저로 직접
접속"**이라는 답변을 받아, Browser pane의 뷰포트 에뮬레이션/표시 방식에 따른 도구 아티팩트일
가능성은 배제했다.

## 2. 현재까지의 결론

- **코드(CSS) 자체의 가운데 정렬 로직은 정상**이다 — 800px~1920px 전 구간에서 오차 0px로
  확인. 이 세션의 환경에서는 "오른쪽으로 쏠림" 현상이 재현되지 않았다.
- 따라서 신고된 증상은 사용자의 **실제 PC/브라우저 환경 고유의 변수**(창을 최대화하지 않고
  화면 오른쪽에 배치한 상태에서 데스크톱 전체를 캡처했을 가능성, 브라우저 확대/축소 비율,
  디스플레이 배율(DPI) 설정, 특정 확장 프로그램의 레이아웃 개입 등)일 가능성이 유력하나,
  이 세션에서 사용자의 실제 화면을 직접 볼 수 없어 **확정하지 못했다** — 짐작으로 "이게
  원인"이라고 단정해 임의로 코드를 고치지 않았다.

## 3. 조사 과정에서 별도로 발견한 실제 결함 (확정)

정렬 신고와는 무관하게, 같은 화면을 점검하던 중 아래 결함을 실측으로 확정했다:

**버튼·입력 요소가 전체 폰트(Pretendard)를 상속받지 못하고 브라우저 기본 폰트(Arial)로
렌더링됨.**

```
getComputedStyle(라벨/제목).fontFamily      → "Pretendard, -apple-system, ..."
getComputedStyle(<button>).fontFamily       → "Arial"
getComputedStyle(<input type=file>).fontFamily → "Arial"
getComputedStyle(<input type=checkbox>).fontFamily → "Arial"
getComputedStyle(<a class="submit-button">).fontFamily → "Pretendard, ..." (정상 — <a>는 폼 컨트롤이 아니라 상속됨)
```

- **원인**: `frontend-apply/app/globals.css`, `frontend/app/globals.css` 둘 다 `body`에만
  `font-family: Pretendard...`를 선언했고, `button`/`input`/`select`/`textarea`에 대한
  `font-family: inherit;` 리셋이 빠져있다. 브라우저 기본 스타일시트는 폼 컨트롤에 별도의
  시스템 폰트를 적용하므로, 명시적으로 상속시키지 않으면 이렇게 깨진다.
- **범위**: 이 한 화면만이 아니라 **지원자 앱(3002)과 관리자 앱(3001) 전체의 모든
  버튼·입력창**(로그인/회원가입/이력서 제출/관리자 판단 화면 등)에 동일하게 해당.
- **근거**: `frontend/app/globals.css` 262번째 줄, `.interview-room__composer textarea`에만
  `font-family: inherit;`가 개별적으로 붙어있는 것을 확인했다 — 과거 누군가 이 문제를
  텍스트에어리어 한 곳에서만 발견해 국소적으로 고치고, 전역 리셋 규칙은 추가하지 않았던
  것으로 보인다.
- **처리 여부**: 사용자가 "정렬 문제"로 지목한 것은 이게 아니라고(카드 위치 쏠림) 확인했으므로,
  **이 결함은 사용자 승인 없이 임의로 수정하지 않았다.** 별도 확인 후 진행 예정.

## 4. 사용자 확인/조치 요청 사항 (다음 단계)

1. 문제가 재현된 그 브라우저 창을 **최대화한 상태**에서 다시 한번 같은 화면을 봐주실 수
   있을까요 — 창이 최대화되지 않은 채 화면 오른쪽에 떠 있으면 카드는 그 창 안에서는
   가운데지만, 데스크톱 캡처 전체로 보면 오른쪽에 쏠려 보일 수 있습니다.
2. 브라우저 확대/축소가 100%인지 확인 부탁드립니다(Ctrl+0으로 초기화).
3. 그래도 재현되면 — 어떤 브라우저(크롬/엣지/웨일 등)인지, 모니터 해상도가 어떻게
   되시는지 알려주시면 그 조건 그대로 다시 재현을 시도하겠습니다.
4. 위 3번 항목(버튼/입력창 폰트가 Arial로 깨지는 문제)은 화면 전체에 걸친 확정된 결함이라,
   같이 고쳐드려도 괜찮을지 확인 부탁드립니다 — 텍스트만 폰트를 바꾸는 순수 CSS 수정이라
   기능에는 영향이 없지만, 두 앱의 공용 CSS 파일을 고치는 것이라 말씀하신 원칙대로 먼저
   여쭤봅니다.
